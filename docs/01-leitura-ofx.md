# Leitura e serialização OFX — Etapa 1

`carregar_ofx(caminho)` lê os bytes uma vez, mantém a interface `(header, ofx)` e integra `controller/ofx_io.py` ao programa principal. OFX 1.x continua sendo interpretado pelo ofxtools 0.9.5; OFX XML com ou sem instrução OFX é convertido por ElementTree e pelo modelo ofxtools. BOM UTF-8 é aceito. A saída é OFX 2.03 XML em UTF-8, com declarações coerentes; ElementTree escapa caracteres e substitui a dupla conversão e formatação com minidom. O leitor aceita também o cabeçalho 1.x e corpo XML criado pela versão anterior.

Para SGML com `CHARSET:1252`, ambas as decodificações são avaliadas estritamente em memória. Se CP1252 falha e UTF-8 funciona, usa-se UTF-8 com `OFXEncodingWarning` e a estrutura OFX ainda precisa passar pela conversão. Se UTF-8 falha e CP1252 funciona, usa-se CP1252. Se ambas funcionam mas produzem textos distintos, a leitura interrompe com `OFXEncodingAmbiguaError` antes de retornar um modelo. ASCII, que produz o mesmo texto em ambas, segue normalmente. Se ambas falham, ocorre erro de decodificação. Nenhuma dessas verificações prova a intenção do emissor.

Após verificar a origem, o chamador pode repetir `carregar_ofx(caminho, codificacao='utf-8')` ou `carregar_ofx(caminho, codificacao='cp1252')`; a escolha é estrita e limitada a SGML com `CHARSET:1252`. A interface atual não oferece menu para resolver a ambiguidade: a integração interativa pertence à Etapa 3. Outros charsets seguem o ofxtools. Os arquivos reais fornecidos foram guardados separadamente e não foram usados nestes testes.

O modelo ofxtools normaliza inicialmente datas a UTC. Para `DTPOSTED` com deslocamento explícito, a conversão restaura o deslocamento e nome do fuso a partir dos elementos da transação; se a associação das transações falhar, a leitura é interrompida. Valores monetários permanecem Decimal. Ausência de transações é aceita. Fuso de outras datas pode ser normalizado a UTC pelo ofxtools; tags desconhecidas são sujeitas às regras da biblioteca. Namespaces XML e variantes institucionais não cobertas pelos testes não são garantidos. A validação bancária e a política de datas futuras ainda requerem amostras adicionais.

A escrita comum recusa destino existente e usa criação exclusiva; o mesmo caminho da origem é recusado. A atualização do OFX Geral mantém a exceção necessária para atualizar o histórico já existente, ainda com escrita direta: interrupções podem danificá-lo até a Etapa 4. A leitura não escreve no original. Preservação é testada byte a byte; nenhuma garantia é dada contra alterações externas concorrentes. O aviso de recuperação automática deve ser acompanhado pelo usuário.

Teste: `venv/bin/python -m unittest discover -s tests -v` e `venv/bin/python tests/fixtures/smoke_baseline.py`. Os testes históricos de parser direto caracterizam a biblioteca antiga; os testes de produção estão em `tests/test_leitura.py`. As falhas esperadas de deduplicação, escolha de diretórios e recuperação de gravação permanecem fora do escopo.

A saída OFX 2.03 foi relida pelo parser `ofxtools` e pelo leitor do projeto com dados sintéticos; FITID, valor, descrição e data local foram conferidos. Softwares externos que aceitem apenas OFX 1.x podem rejeitar a saída; nenhuma compatibilidade externa foi testada.
